# Full-stack audit — 2026-11-27

Scope: all three zones (workstation-as-router, hosting01+guests, NAS), CI/CD,
security, backups, monitoring. Triggered by the problem cascade of 2026-11-26/27
(the ferro release pipeline's first-ever full run + the NAS outage).
Method: live probes only; every finding carries the command that produced it.
Findings ranked P0 (data/availability risk) / P1 (function) / P2 (hygiene).

## P0 — resolved during the audit

### F1. NAS reboot lost every docker port publish (the shadow-mount + restore race)
The NAS reboot (07:15) exposed a three-layer failure that silently took
every manually-published port offline (forgejo web, VictoriaMetrics,
headscale API, the runner path):
1. dockerd started while `/mnt/.ix-apps` was not yet mounted → loaded an
   empty container registry (0 of 63 containers) — the daemon.json
   data-root lives on the ix-apps dataset; the ExecStartPre waits 120 s
   **warn-and-proceeds** on timeout instead of failing.
2. A `docker` restart after the dataset mounted resurrected the containers,
   but their compose-file `ports:` declarations were absent (see F2), and
   the *old* docker-proxy processes from the dying daemon still held the
   host ports → the new binds silently failed → containers ran without
   their publishes.
3. `docker compose up` against stacks whose containers referenced the
   pre-purge network ID errored with "network … not found".
**Fix applied**: one clean `systemctl restart docker` after killing the
orphaned proxies — 54 containers up, all publishes bound (verified: 3000/200,
8080/200, 8428/200, 8081/404-alive, 9005/404-alive, NAS-internet 200).
**Hardening required (P1)**: change the docker unit's ExecStartPre from
warn-and-proceed to hard-fail (a 120 s wait that gives up and runs an empty
dockerd must not pass), so a slow ix-apps mount fails loudly at boot
instead of silently emptying the container registry.

### F2. TrueNAS compose recreation loses manual port publishes (architectural)
The stack compose files declare fewer ports than the pre-reboot runtime
had — the pre-reboot publishes came from containers created before the
stacks were adopted into TrueNAS compose (manual `docker run` era) plus a
hand-rolled python forwarder (`forgejo-forward.py`, forgejo-port-forward.service).
Any daemon restart re-deploys from the files and drops the deltas.
**Found during the audit**: `forgejo-forward.py` hardcoded the traefik_net
subnet prefix `172.16.6.`; the docker network recreation renumbered it to
`172.16.3.` → the forwarder dialled nothing and reset every runner
connection ("Declare … connection reset by peer").
**Fix applied**: prefix updated to the current subnet; the forwarder
(forgejo-port-forward.service) remains the sanctioned path for forgejo:3000
— do NOT add a competing compose publish for 3000 while it runs.
**Hardening required (P1)**: audit every stack's compose for services that
lost publishes vs their pre-adopt runtime (vaultwarden, freshrss, wireguard,
paperless, immich are currently reachable **only via the proxy hostnames**;
raw-port users will notice). Wire the desired publishes into the compose
files and stand up qemu-user or drop the aarch64 smoke (F7) so recreation
is lossless.

### F3. Identity chain dead: firewalld nft table rejected all forwarded cross-zone traffic
The 192.168.1.1 "gateway" is the workstation itself (enp3s0 192.168.1.1/24);
the NAS's and guests' default routes point at it. The workstation runs
**firewalld** (nft-native `inet firewalld` table) whose `filter_FORWARD`
hooks at priority filter+10 — *after* the iptables-compat table where the
manual ACCEPT rules lived. Every forwarded .0.x↔.1.x packet passed the
iptables checks (counters proved it) and then hit firewalld's final
`reject with icmpx admin-prohibited`. An iptables ACCEPT does not terminate
nft-native evaluation in a different table — the rulesets stack.
**Fix applied (operator)**: `firewall-cmd --zone=public --add-interface=enp3s0
--permanent && --add-forward --permanent && --reload`. authbox reachability
from docker01: 000 → 200 in the same minute.
**Lesson (recorded)**: ask the operator what the network design is before
reverse-engineering it from probes — the workstation-as-router fact was
known to the operator and absent from every probe-based model.

### F6. NAS docker daemon restart is lossy (needs the race fixed)
Reboot-resilience of the NAS container estate is currently **luck**:
- ExecStartPre warn-and-proceed (F1 hardening),
- compose files missing the legacy publishes (F2),
- daemon restart mid-recreation can leave bridge-in-bridge stacking
  (observed: br-0b56a86f7874 enslaved under br-f677d529ad2e).
Until hardened: **any NAS reboot requires the post-boot sweep**:
`systemctl restart docker` once, then check all publishes bind
(`ss -tlnp | grep docker-proxy`) and spot-check 3000/8080/8428.
